## Question and pre-registration
Can an evolutionary search over a DSL that now includes F_p arithmetic, S_3, point lifting and linear algebra find a DLP procedure whose
cost, measured at sizes 2^17-2^20 never used by the search, beats the same-DSL rho control in *growth* (not just constant)?
PROTOCOL.md was written and hashed before any search: sha256 `83d4df9db486d2b68452e8272141f942cab458c063e83aaae9326e464edc6909`
(unchanged at the end; evolve2.py/evaluate2.py assert it). It fixes: train 2^10-2^12 (seeds 500/501), validation (550/551), fit sizes
2^13-2^16 (600-602), held-out 2^17-2^20 (700-702, 40 instances x 3 curves per size), identical instances for candidates and controls,
and a four-part success rule applied on held-out sizes: T1 success >= 0.9 everywhere; T2 slope of ln(cost/rho cost) vs log2 r with 99%
bootstrap upper bound < 0; T3 out-of-sample test: fit cost = alpha*sqrt(r)+gamma on 2^13-2^16, predict 2^20, double ratio
Q = (obs/pred)_cand / (obs/pred)_rho has 99% upper bound < 1; T4 mean cost at 2^20 below rho. No log-log exponent is used anywhere.

## Method
- Fast curves (curves.py): numpy point counting + table build; a prime-order 2^20 curve takes 3.4 s (2^16: 0.2 s), cached (git-ignored
  `cache/`, 70 MB, regenerable and deterministic in (tb, seed)). Curves up to 2^20 were used.
- dsl2.py: all 19 round-16 ops plus FCTR, FCONST, FADD, FMUL, FINV, FSQRT, FRHS, FLEG, FRAND, FX, FS3 (a root of S_3(x1,x2,.)), FS3EV
  (evaluate S_3), LIFT (field element -> point, a new "factor-base generator" whose log is hidden), IFOK, IFSMALL, RELATE (records
  A +- B +- C = 0 if S_3 holds), MSOLVE (Gaussian elimination mod r, <= 400 rows, <= 255 generators, cost rows*cols*min/12). Field-op costs
  in group-op units (mult 1/12, inversion 1, sqrt 0.125 lg p, ...). Declared changes from round 16: relation signs read from the
  hidden log (= comparing y); LOOK/SOLVE use full-x equality (a real hash table with full keys) so partial-key false hits are not charged.
- Hand programs in the same DSL: rho_dp (the control), rho_dp variants (nb=3; dpbits=3), Floyd rho with restarts, BSGS, and an
  index-calculus-style program (prog_ic / prog_ic_ms: random walk point R, factor base = x < p^(14/32), solve S_3(x1,x2,xR)=0 for x2,
  keep if small, LIFT both, RELATE, MSOLVE). prog_ic_ms genuinely solves instances (verified: success 0.63-1.0, sizes 10-14 with a
  400*sqrt(r) cap), so index-calculus-like procedures are expressible and the linear algebra is correct.
- Search: 4 runs x 120 generations, pop 100 (each completed in 95-121 s, i.e. one slice, so no checkpoint resume was needed): r0, r1 random
  start; s2, s3 seeded with hand programs (secondary). Fitness = mean over training sizes of cost / (rho_dp cost on the same curve) +
  slope term rewarding a falling ratio + parsimony; no log-log exponent.
- Commands (all via `research.py exec`; evidence files `RUN-885e...-command-*.evidence`): `8a282cdf` search (run_slice.sh); evaluation
  `96311aa1` and `68ac9681` crashed (a syntax error I wrote, then a division by zero for the all-zero-cost empty program of r1), `70bdc0a2`
  failed (log of a non-solver), `0ad06db0` final evaluation of r1, s2, s3; the controls + r0 results were printed in the evidence of the
  second-to-last invocation (`96311aa1`, outputs also in out_eval_controls.json, out_eval_r0.json); `ab7c4766` ic_scaling.py. Failed
  invocations are real failures that I fixed (evaluate2.py was edited after PROTOCOL hashing; the protocol file itself was not).

## Mechanisms of the champions (manual reading, evolved programs in out_evolve_*.json)
- r0: single STEP-walk (table-based pseudo-random steps) with INS/LOOK of the same register keyed on low x bits (no restart, no
  distinguished points): "rho with memory". Cost ratio to rho_dp rises to 2.0 at 2^20 and success drops to 0.82 because the 2*sqrt(r)
  table fills and then stops recording (cap M) - a memory-bound failure, not a new mechanism. The FRHS/INS fragments in other
  hall-of-fame members are dead code (F registers never read).
- s2: a mutated BSGS (seeded from the hand BSGS): SETC constants, a first phase of ADD+INS (baby steps, 20-bit key) for r^(14/32)
  iterations, then ADD of a constant register and LOOK each step (giant steps) after r^(18/32); FCONST in its init writes a field
  register nobody reads. I did not verify the exact step split beyond this reading. Same Theta(sqrt r) table structure as BSGS;
  alpha 1.39, gamma 10.
- s3: BSGS variant with a conflicting extra INS/LOOK; fails T1 at 2^18 (0.83).
- r1: converged to the empty program (fitness plateau; the shaping credit never fired). Search power of the random-start runs is low
  (2 of 4 found a working solver), same as round 16.
- No evolved champion used any F_p arithmetic, S_3, LIFT or MSOLVE operation with effect (every field op in a champion is dead code or a
  no-op). I did not count the ops across all individuals ever evaluated (unmeasured); the seeded initial population contained prog_ic_ms
  (train fitness 3.6 = 3.6x worse than rho_dp, success 0 under the 12*sqrt(r) cap) and selection removed it. So the new instructions were
  expressible but not selected: either they never help under this cost model, or the search is too weak to assemble the 8-10 instruction
  index-calculus pipeline from random start. The second is not excluded; the first is supported by the mechanism analysis below.

## Why index calculus does not fit under the cap (analysis, not a theorem)
In the DSL an S_3 decomposition R = +-f1 +-f2 with both x-coordinates in a factor base of size B succeeds with probability ~B/p per
(R, x1) trial, each trial costing ~10 group-op equivalents (STEP 1, LIFT ~2.5, FS3 ~3, LIFT, RELATE). Collecting ~B relations then
takes ~10p trials, independent of B, and the elimination adds ~B^3/12 (the cost rule; sparsity not exploited). Hence cost >> sqrt(r)
once p ~ r >= 2^10. Measured (ic_scaling.py, 400*sqrt(r) cap, 3 curves x 20 instances; success in brackets): cost/sqrt(r) of
prog_ic_ms = 189 (0.63), 127 (0.95), 162 (0.90), 180 (0.88), 266 (0.73) at 2^10..2^14, versus rho_dp 5.5, 4.5, 3.6, 3.4, 2.8. So the
index-calculus/rho cost ratio grows from 34 to 96 and its success under a 400 sqrt(r) cap falls with size: consistent with ~p growth and
with the known fact that elliptic-curve prime-field index calculus has no advantage over rho for n = 2 decompositions. Only a few sizes
and a hand program: this is a consistent record, not a bound.

## Claims, deviations and limitations
Experimental evidence only (no proof, no Lean). Claim supported: in this instruction set and at 2^10-2^20, evolutionary search with
field/S_3/linear-algebra primitives and a rho-ratio fitness finds nothing that beats the rho control's growth; the best evolved programs
are BSGS-like constant-factor variants with flat cost ratio (CI contains 0), and the others fail T1. Not claimed: any speedup, anything
about larger sizes or other model features (y-bits, CM structure, higher summation polynomials S_4+, sparse linear algebra).
Deviations/limits: (1) 4 runs, 120 generations each (short: ~2 min per run; the budget was not the constraint, I did not extend the
search beyond the pre-registered 4 runs); (2) evaluate2.py bugs fixed after hashing PROTOCOL.md (listed above), no change to the
criteria; s3 and r1 were not run through T2-T4 because T1 failed; (3) the model is a generic-cost VM in which a point carries hidden
logs, same caveat as round 16; (4) wide CIs at 2^20 (120 instances); (5) multiplicity: four champions + five controls at 99%;
(6) the held-out curves 17-20 share the generator with the training curves (same family, different seeds); (7) the index-calculus
program is hand-written and uses only 2-decompositions; MSOLVE cost is dense-elimination cost.
