2. **The end-to-end reduction works exactly as theory says on a planted leak, and costs poly(log r)/ε², not √r.** Interval-free multiplicative self-reduction (stride-ML refinement) recovers k with success 200/200 verified at ε ∈ {0.2, 0.1} and 39/40 at ε = 0.05 (the one miss at r = 2437 ≈ 2^11.25) at a cost nearly flat in r. But the user's "majority vote over random known shifts + binary search" **does not work for an MSB oracle**: additive shifts give one non-repeatable query per threshold (measured success 0–4/200 for ε ≥ 0.05 vs 200/200 for a perfect oracle; matches (1/2+ε)^{log₂ r}).
3. **The bar.** For the stride-ML pipeline to beat my same-implementation rho control: ε ≳ 0.055 (free oracle) / 0.16 (7 group ops per oracle call) at r = 2^28; ε_bar ≈ C·r^{-1/4} with C growing slowly (≈ 7 → 10 over 2^28 → 2^64 for free oracle, 20 → 28 with 7 ops/query). 4. **No speedup is claimed**; the speedups measured here exist only on the planted control, whose oracle is a lookup of the secret by construction.

## 1. Mechanism (inventor item 1)
Idea: estimate k, then finish by search. Information-theoretic requirement: Q = kP is the only input; any estimator is a function of Q (and P, curve). A hard-core-bit style argument says an MSB oracle with advantage ε is as good as full ECDLP. What I could and could not retrieve (web search this session; **I read search-result summaries, not the primary papers**):
- Boneh–Shparlinski (CRYPTO 2001): the *least significant bit of an x or y coordinate of the Diffie–Hellman value abP* is hard-core in the sense that a predictor for it on a family of curves gives the whole DH value, via the hidden number problem; the result is in the model where the oracle may take a homomorphism/changing representation; follow-ups: Jetchev–Venkatesan (CRYPTO 2008, LSBs via isogeny random walks), Fazio–Gennaro–Perera–Skeith (CRYPTO 2013, every bit and segment predicate of ECDH), González Vasco–Näslund–Shparlinski (PKC 2004, non-negligible advantage excluded for larger fractions of bits). A 2016 survey (arXiv 1607.01842) states that no method is known to prove hardness of single bits of DH keys in the usual (fixed representation) model.
- Akavia–Goldwasser–Safra (FOCS 2003; Akavia PhD thesis 2008): Fourier list-decoding (heavy-coefficient learning over Z_N) proves segment predicates (incl. MSB-type) hard-core for dlog-type one-way functions, a secondary source says for the O(log log N) most/least significant bits; Rafols–Morillo extended to middle bits. Håstad–Näslund and Blum–Micali (MSB of dlog in Z_p*) are cited from memory only, not re-verified.
- These concern bits of the *DH secret* or segment predicates of a one-way function, not an oracle for MSB(k) *given Q = kP in a fixed prime-order group with fixed encoding*; I use the direct ECDLP analogue and derive the decoder myself (below). I have not proved its poly(log r)/ε² query bound in general; I measured it on a planted control.

Self-reduction (derived here): for known c, the point cQ = (ck mod r)P is uniform over the group when c is uniform and k is fixed, so an oracle with average-case advantage ε on uniform points has advantage ε on every query cQ. The bit b_c ≈ MSB(ck mod r) = [frac(c·θ) > 1/2], θ = k/r: a noisy square wave in c with frequency θ, i.e. a code word of a Fourier-heavy character; k is the heavy frequency. Majority-over-shifts would require the *same* target bit at each query; the additive shift Q + aP gives MSB(k + a) = arc membership at a non-repeatable point, so it supports only P0 (below), not amplification. Cheap variant used in P1: c = j·m for j = 1..N (one group op per query after one scalar multiplication mR); ML over a grid of 4N frequencies; the residual window shrinks by about N/(2κ) per round; "estimates within estimates" = repeat on R = (k − ĝ)P with stride m = r/(2W). Caveat recorded as an obstacle (§6): this structured-multiplier query set (scalars j·m·d mod r) is not uniform, so an oracle's average-case guarantee does not cover it; the random-c version covers it but needs full scalar multiplications per query (≈1.5 log₂ r ops) and a list-decoding step (KM/AGS), which I did not implement beyond brute-force ML.

## 2. Pseudocode and prototype (item 2)
Code in `round20-inventor-j/`: `feat.c` (C feature generator: Q, Q±jP (j ≤ 3), 2Q, Legendre symbols; verified against Python ops), `learn.py` (features, models, splits, controls), `pipelines.py` (Ops-counted pipelines, rho, kangaroo), `run_ctl.py`, `run_p1.py`, `run_other.py`, `analyze_learn.py`, `analyze_costs.py`.
```
ESTIMATE-MSB(Q, P): features F(Q,P) -> model -> bit            # §3 of protocol; models: HGB, MLP(128,64), logistic, best single feature
P0 additive binary search: lo=0,hi=r; while hi-lo>1: mid; a=r/2-mid; b=O(Q+aP); b? hi=mid : lo=mid
P1 stride-ML(Q): g=r/2, W=r/2; loop: R=Q-gP; m=r//(2W); N=ceil(nu*ln(4N)/eps^2) (fixed point);
      for j=1..N: pt_j = j*m*R (1 op each after m*R);  b_j = O(pt_j)
      d^ = argmax over 4N grid points d in [-W,W] of sum_j sgn(b_j) * sgn(MSB(j m d mod r));  g += d^; W <- ceil(kappa*2W/N)
      until W<=3; enumerate d in [-W,W]; return k with kP==Q
P2 interval + kangaroo: [lo,lo+w] -> Q'=Q-lo*P; tame at wP, wild at Q'; mean jump sqrt(w)/2, DPs, restarts counted.
P3 iterative scale-aware regression oracle: khat=k+N(0,(rho*W)^2) around residual; window <- khat +- z*rho*W; repeat; (non-scale-aware: noise rho*r fixed)
P4 closeness scan: 32 centers over the window, T shifted tests each, planted detector D(R,w)=[|d|<=w] xor noise(1/2-delta); ML over 8*32 positions; window shrinks 16x/round; finish when W<=300 by enumeration.
```
## 3. Correctness (item 3)
Every pipeline verifies kP = Q before output (verification counted), so a returned k is correct; failure = window lost or ML error. Measured success per cell is reported. P1 correctness rests on the planted oracle's per-point independent noise (hash of the point, advantage exactly ε in expectation), decode = ML, window update width κ·2W/N with κ = 2 and N from ν = 2 (calibration: ε = 0.1, 20 bits, 30 instances: ν = 1: 24/30, 1.5: 29/30, 2: 30/30, 3: 30/30; κ = 3 same) — the registered rule (≥ 95%, set {0.5,1,2,4,8}) selects ν = 2.
**What the control is**: planted oracle functions of the point, computed by the simulator from the secret scalar it tracks (equivalent to a curve family defined by its dlog table). The control tests the decoder machinery and the cost model, not the existence of a leak.

## 4. Complexity model (item 4)
Counted ops: affine add/double = 1 op (same `Ops` as the rho control); per-oracle-call feature cost m_q = 7 group ops (Q±P, Q±2P, Q±3P, 2Q; reported separately as "core" vs "+7/query"). Non-group compute (ML grid 4N², features) is not charged and is reported as a caveat: ML decode is O(N·G) numpy work, N·G = 4N² ≈ 2.8·10^9 at ε = 0.05.
P1: rounds ≈ log(r/6)/log(N/(2κ)), queries N(ε) ≈ ν·ln(4N)/ε² per round, cost ≈ rounds·(N(1+m_q) + O(log r)); model vs measurement at 2^28: ε=0.2 12231 vs 12056; ε=0.1 42996 vs 42895; ε=0.05 200394 vs 200231 (with features; agreement ≤ 1.5% for ≥ 16 bits). Memory O(N). Preprocessing: model training (not charged). Success probability measured (below).
Fits (no log-log): rho control ops = 1.249·√r + 346 (alpha 95% CI [0.898, 1.580], gamma CI [-57, 784]; 135 instances, r 2^12..2^27.3); kangaroo control ops = 3.352·√w + 424 (alpha CI [2.80, 3.87]; 270 instances, w 2^8..2^24, success 1.000). ## 6. Exact obstacle (item 6)
1. **There is no leak to estimate.** The coordinate maps k ↦ x(kP), y(kP), x((k±j)P), x(2kP) are, empirically to ±0.003, independent of MSB(k), of θ = k/r and of |k − g| < r/32 for every feature family and model tried, on held-out curves and held-out k; consistent with the lab's earlier equidistribution analysis (HYP-130de9b1, HYP-80158648) and the round-10 learned-bit-predictor null (RUN-071d1da9). Weil-bound equidistribution of twisted sums predicts exactly this as p → ∞.
2. **Even a genuine leak must beat ε ≳ C·r^{-1/4}.** The self-reduction is not the bottleneck: poly(log r)/ε² queries decode k, but 1/ε² · polylog must be below √r·1.25, which is ε_bar ≈ 0.055 (2^28, free oracle) … 1.6e-4 (2^64). A predictor that is *just* detectable at the 10^-3 level at toy sizes is far below the bar at the sizes where it matters (it must be ~ r^{-1/4}, e.g. 0.008 at 2^40) and cannot be measured at 2^64+ (n ≳ 1.6·10^8 test samples per ε = 1e-4 alone, and the curve cannot be generated at that size by this pipeline).
3. **Scale.** "Estimate then search" needs a *scale-aware* estimator. A fixed-error estimator stalls (P3 non-scale-aware: width stuck at 2zρr; real regression error = whole circle) and kangaroo on width w costs 2.7x rho at equal width.
4. **Query-set caveat for the cheap decoder**: P1 queries c_j R with structured scalars; average-case oracle advantage guarantees nothing for those. The uniform-c version costs ≈1.5·log₂ r extra ops/query (included only in the bar through m_q ≥ 7 sensitivity m_q = 50) and needs sublinear heavy-coefficient search; brute-force ML over r candidates is Θ(rN) non-group work.
5. **Additive majority voting is not amplification for MSB** (P0).
6. Resolution: 99% half-width 0.003 at ≥ 2^20 (n = 2·10^5) does not exclude advantages in [0, 0.003]; Weil-type bounds suggest they vanish as p → ∞ but that is an equidistribution heuristic, not a proof, and only prime-field curves ≤ 2^27.3, 12 curves/size, 4 model classes, 160 features were tested.

## 7. Verdict against the bar
Does any real-curve estimator have a non-vanishing advantage out of sample? **No**: all 40 MSB cells, all regression cells (error 0.25 = guess) and all closeness cells with a working control are null; 99% CI upper bounds on MSB advantage over all four models 0.0045 (2^28), 0.0032 (2^24), 0.0031 (2^20), 0.0065 (2^16), 0.0198 (2^12; low power) against bars 0.055–0.16 (2^28, depending on oracle cost), 0.10–0.32 (2^24), 0.19+ (2^20). Controls pass: planted MSB leak flagged at all sizes by boosted trees (MLP weaker; 12-bit low-power), planted regression and closeness leaks flagged at ≥ 2^16 (closeness w=2^8 control not flagged: that cell is inconclusive). The planted pipelines work end to end (P1: 100/100 at ε = 0.2, 100/100 at ε = 0.1, 39/40 at ε = 0.05), costing 2^28: 1.8k–25k core ops vs rho 16.7k, which is a statement about hypothetical oracles of advantage ≥ 0.05.
