## 1. Mechanism (inventor item 1)
Question: with advice A built once for a fixed (p,a,b,P,r), can online time T (counted group ops; comparisons, probes, bit access free but reported) satisfy S·T² ≪ r?
Information-flow view: Q enters the algorithm only through the outputs of group operations (points Q+cP) and Q's own coordinates. Non-generic gain needs either
(a) the map k → x(kP) leaks structure to comparisons/bits (E2), or (b) a step function/DP rule tuned to this curve increases coverage per stored entry (E3), or
(c) a distribution effect of x making search cheaper than hashing (E1).
- E1: sort x(jP), j ≤ S, interpolation search, giant steps Q − c(2S+1)P.
- E2: greedy best-first information-gain decision tree over features of x(Q), x(Q+P), x(Q−P): 32 bits and 15 quantile thresholds each (141 binary features), T = 2 ops, node budgets 15/255/4095, labels top-4 bits of k' = min(k, r−k) and k' mod 16.
- E3: C2-style DP walk table with a curve-tuned step family (F0 uniform 31 parts; F1 small steps w=64/4096; F2 multiplicative-hash partitions R=16/64/256; F3 powers of two), DP rule, m, L and table seed chosen by minimising training ρ on 48 candidates (B0 = best of 12 generic-grid candidates, F0 only).

## 2. Pseudocode and prototype (item 2)

## 3. Correctness (item 3)
E3: a table entry is the exact point (x,y) = uP; an online point Q+tP+Σ a_jP equal to it gives k+t+Σ ≡ u (mod r), so k = u−t−σ; the output is verified by kP = Q (cost counted).
Wrong outputs are impossible; failure = no DP match within 400 trials. Observed success 1.000 for every reported evaluation (all curves, B0 and H, evalA and evalB). E1: all 16200 queries verified (ok = nq in all 54 configurations).
E2 makes no claim of correctness (it is a null test with positive control).

## 4. Complexity model (item 4)
Cost: affine point add/double = 1 op (inversion not separated; same for all variants). T = mean ops per query including failed trials and the verification (≈1.5·bits ops
per scalar multiplication; this inflates ρ at small sizes, see §6). S = stored distinct DP entries (key point + scalar, ~12 bytes). Step-point setup (≤256 multiplications) and query generation are not charged.
Preprocessing is reported separately (`prep`). Random-like expectation: m ≈ L ≈ r^{1/3} gives S ≈ r^{1/3}, T ≈ r^{1/3}, prep ≈ r^{2/3}, so ρ = Θ(1). Tuning cost for H: 48 table builds + 7200 training queries ≈ 48 × prep ≈ 50–100 r^{2/3} ops, not included in the table prep.

## 6. Exact obstacle (item 6)
1. **What a fixed curve could, in principle, offer** that the generic bound (averaged over encodings) does not forbid: exploitable structure in k ↦ x(kP) or in the group-op implementation. Every channel I could test is closed: (E2) comparisons/bits of x(Q), x(Q±P) have no measurable information on k or k mod 16 (null with power; control passes); (E1) the x-distribution only makes lookups cheaper, never fewer group ops.
2. **Why tuning cannot beat the birthday structure.** Online information about k arrives only through exact point collisions with advice points. For a step map f(R) = R + a_{h(x(R))}P the scalar-side map k ↦ k + a_{h(k)} has the statistics of a random mapping whenever the labels h(k) = H(x(kP)) are pseudorandom (the E2 null is the empirical support for that). A table of S DP entries with walk length L covers ≈ S·L points, an online trail covers ≈ L points: collision probability ≈ S·L²/r, so ρ = S·T²/r = Θ(1) with T ≈ L. Tuning only moves constants through extreme-value selection among N candidates (measured: ≲ 12–15% at 32 bits, not significant, with winner's-curse shrinkage). A step family with coverage ≫ S·L per DP would need a contracting, non-random functional graph on Z_r that is still computable from x-bits of the current point; no such family appeared among 7 structured ones (small-step "kangaroo" steps were worst: median ρ 18).
3. **The missing statement.** No bound exists for one concrete curve (CGK/CDG: averaged over random encodings; E0'-type remark in RUN-98e2c896: tautological for fixed encodings). So this null is empirical, at ≤ 2^32 and for the listed feature/step classes only; it neither proves S·T² = Ω̃(r) for this curve nor rules out advice that encodes arbitrary function of the whole table (e.g. compressing the k ↦ x map): such compression would need the map to be compressible, which is exactly the "no k-informative structure" question left open.
4. Small-size artifact to avoid in future work: ρ over 16..24 bits is inflated by verification and rounding and falls for any variant; slopes must be judged from ≥ 24 bits and against an untuned control.

## 7. Verdicts against pre-registered rules and limitations
- E1: descriptive; no improvement. E2: no leak (0/90), control passes. E3: slope half of rule met trivially (B0 also), comparison half not met; confirmatory replication fails. **No success claim.**
- Limits: r ≤ 2^32 (3 + 3 curves per size, 4 sizes ≥ 24 bits), toy sizes, one cost model (affine ops), one DP/step design family, tuned candidates 48, E2 features low-complexity only. Winner-picking used training queries disjoint from evaluation queries; table seed was part of tuning for evalA (hence evalB).
- Hypotheses to record: "tuned step/DP functions give a statistically significant ρ gain" → not supported (≤ ~12%, CI includes 1). "k ↦ x(kP) comparisons leak k" → not supported on the tested classes.
