## Check 6: the flagged gap (did inventors B and C model setup cost?)
Determined from run reports and code; the answer differs for B and C, and the paper's single wording is imprecise.
- **Inventor B (RUN-58dee679, `round12-inventor-b/ecinv.py`, `analyze.py`).** `rho` counts "EVERY add/double incl. table construction" (docstring, ecinv.py line 99); the cost model in the run report includes setup (`~3*1.5 log r + m + 200 adds`, m=256 table). So setup is *in* the measured cost, and the fit is a pure log-log slope (`log2 mean ops` vs `log2 r`), with no additive term. Hence B1 exponents (0.437, 0.451, plain rho 0.465/0.492) are exactly the kind of naive fit the paper warns about. The report's own B2 analysis demonstrates the bias: with `W=10` the pre-registered rule printed "asymptotic improvement" (slope 0.373) because overhead share fell 0.60 to 0.03 (analysis.txt lines 34-35).
- **Inventor C (RUN-aabd43b1, `round12-inventor-c/PROTOCOL.md` lines 13-14).** The one-time step-table setup (`~93 log2 n` ops) is *excluded* from `ops` and reported separately as `setup`; the primary metric and fits are on `ops` excluding setup. The fits are also pure power laws without a gamma term, so other fixed costs (distinguished-point overhead 1/theta per trail, fixed r=31 walk) remain unmodelled, but setup in the B sense is not in the C exponents. For C2 the preprocessing exponent 0.62 is reported separately, as the paper says.
- **Is the paper's wording right?** Partly. "The ledger records some with confidence intervals but does not say that setup cost was modelled" is literally true of the HYP records, but the question is answerable from the run reports and the paper could now state: B1 includes setup and is power-law fitted (bias plausible, cf. B2); C excludes setup by protocol and is power-law fitted (setup bias not applicable, other fixed overheads unmodelled). Lumping "inventor C" with B as setup-biased fits is over-cautious, not wrong. Recommend replacing the unknown with these two sentences and citing RUN-58dee679 and RUN-aabd43b1. The paper's statement that none was re-fitted is correct; a refit with `alpha sqrt(r)+gamma` on the existing `out_*.jsonl` would close it cheaply.
