## Question and pre-registration
Can an evolutionary search over a small DLP instruction set (ADD/DBL/NEG, x equality/comparison/bit extraction, bounded
hash table, counters, conditionals) find a procedure with cost exponent < 1/2 on sizes and curves never used in the search,
and what does it rediscover? PROTOCOL.md was written and hashed BEFORE any search:
sha256 `961b523b10c7d2ed722f1527dcea9d3c2d1815ed2a6247314978ea3eb19cf6bc` (PROTOCOL.sha256; evolve.py/evaluate.py assert it;
every out_evolve/out_eval JSON records it; file unchanged at the end). Success criterion: success >= 0.9 per size AND the 99%
bootstrap upper bound of the exponent < 0.5 on held-out sizes 13..16 bits (3 curves x 60 instances per size), with a
calibration gate (hand BSGS through the same estimator). Overfitting guard: train 10-12 bits/seeds {0,1}; validation
seeds {150,151}; test-A = sizes 13-16 (all larger than training), test-B = new curves at sizes 10-12.

## Approach and execution
- VM (dsl.py): 19 ops, 4 point registers, 2 counters, hash table <= 2*ceil(sqrt r), program = init (<=5) + body (<=10) loop,
  charged costs (ADD/DBL 1; SETC double-and-add; SETRAND 3*lg r; walk table 6*lg r + 2^nb; each candidate verification
  1.5*lg r; no free oracle), cap 12*sqrt(r). Hand baselines written in the same DSL: BSGS, Floyd rho (restart), distinguished-point
  rho (rho_dp), brute force. A first walk-table construction bug (entries were all multiples of one point, making rho
  degenerate) was found and fixed during DSL smoke tests on training/baseline curves, before PROTOCOL.md.
- Search: population 100, 200 generations, random initial population. A 60-generation smoke test with unshaped fitness stayed on a
  plateau (all programs fail = 12), so fitness shaping (credit for distinct-coefficient x-collisions) was added and registered
  in PROTOCOL.md before the real runs. Evolution then found working solvers in tens of generations.
- Commands (all via `research.py exec`; runs were time-sliced by checkpoint/resume because 200 generations exceed 280 s;
  checkpoint pickles deleted afterwards): run_batch.sh seeds 0-3 (3 slices), seed 2 finishing, evaluate.py baselines /
  random_s0,1,3 / random_s2, supp.py. Evidence: the `*-command-*.evidence` files (two early invocations were killed by my own
  mistakes, `pkill` self-match and a timeout, and restarted; some logs contain duplicate/overlapping lines from the restarts).

- Calibration gate FIRED: BSGS (provably Theta(sqrt r) in this model) has a 99% CI wholly below 0.5 (fixed setup/verification
  overhead biases the finite-range exponent low), so "upper < 0.5" is non-discriminating and the replacement rule applied:
  champion upper99 < BSGS lower99 = 0.434.
- LITERAL protocol outcome: only evolved s1 meets both criteria (success 1.00; upper99 0.426 < 0.434). s0, s2 fail (not solvers
  on test), s3 fails the exponent criterion (upper 0.519).
- Why I do NOT count s1 as a sub-sqrt result (post-hoc analysis, labelled as such): (i) the hand DP-rho program, a known
  Theta(sqrt r) algorithm, scores a lower exponent (0.334) through the same estimator, so the registered gate (BSGS as sole
  comparator, which has smaller overhead) was too weak; the registered statistic cannot separate overhead from exponent.
  (ii) On a fresh curve per size (seed 300, sizes 13-16, 80 instances; supp.py; run hit the 270 s timeout at 17 bits, so no
  extrapolation beyond 2^16 was obtained) cost = alpha*sqrt(r) + gamma fits s1 with alpha ~ 1.78, gamma ~ 139 and hand rho_dp with
  alpha ~ 1.77, gamma ~ 138 (BSGS: 1.53, 29), computed by hand from the printed means (s1 c/sqrt r 3.31, 2.85, 2.45, 2.34; rho_dp
  3.29, 2.84, 2.53, 2.33). gamma ~ 6*lg r + 2^nb + verification, i.e. the walk-table setup. So s1 is statistically
  indistinguishable from rho_dp in cost; its low beta is the setup overhead amortising. No evidence of a different exponent.
  This is a fit to four sizes, not a proof; I did not obtain sizes > 2^16.
- Structure rediscovered (manual reading of s1): init SETO; body is a walk of STEP with nb=4 table (add table entry chosen by x
  low bits) on one register, interleaved INS/LOOK of keys (x>>2) with 17-19 bit width, SOLVE of a register against R0; no
  restart, no distinguished points, table filled with every other step. This is a rho-like (walk + hash collision) program
  with a table-based collision detector, i.e. rho as in "rho with memory", not BSGS. s3: hybrid (additions of a fixed point, DBL,
  INS/LOOK, mixed NEG); cost/sqrt ~ 2.1-2.4, slope 0.456; I did not analyse its mechanism in depth (unverified). s0 and s2
  found only partial/low-yield solvers. No champion used anything beyond the generic operations; no hidden-oracle use was seen in
  s1 (verification is charged and the candidate is derived only from LOOK/SOLVE).
- Train-metric: best random-start champions reach 2.4-3.9 sqrt(r)-units; hand BSGS is ~1.7-1.8; evolved programs did not beat the
  human BSGS in constant either.

## Claims and verification
Experimental only (toy sizes; no proof, no Lean). Claim supported: in this instruction set, unguided evolutionary search
rediscovers rho-like collision programs and fails or does mid-quality otherwise; it did not rediscover BSGS (no champion
uses a baby-step table + giant stride systematically) and found nothing beating exponent 1/2 beyond the setup-overhead artefact.
Not claimed: any speedup. Nothing reviewed independently (single agent, same provider).

## Deviations from PROTOCOL.md (honest list)
1. Only 4 of the 8 pre-registered primary random runs (seeds 0-3) were completed (time budget). Seeds 4-7 not run.
2. Secondary seeded runs (10, 11 planned 10-13) were started but killed at ~generation 80/200 for time; no champion or
   test evaluation. Log: train best ~1.66 sqrt(r) units at gen 80 (not comparable to test numbers).
3. Test-A used 3 curves x 60 instances as registered; the post-hoc supplement (seed 300) is outside the registered design.
4. Evolution was time-sliced with checkpoint/resume; seed 2 and seeded runs had accidental duplicate processes writing the same
   checkpoint (deterministic, same result expected, but unverified).
5. Multiplicity: four champions tested at 99%; the single formal pass (s1) is rejected on interpretive grounds above.

## Outcome, limitations and next action
Negative/uninformative for sub-sqrt: no program beats 1/2 out of sample once setup overhead is accounted for; search rediscovers a
rho-like walk+table structure. Limitations: the constant grid r^(e/32), x-only exposure, the log-range of only 2^13..2^16, the fact
that the model is generic-group-like (sqrt is the expected optimum, so success was unlikely), and low search power (4 runs).
Next: (a) fix the estimator by fitting alpha*sqrt(r)+gamma with a hand rho_dp control before any claim; (b) extend to 2^17-2^20
with faster curve generation; (c) finish seeded runs and the remaining random seeds if the lab wants to repeat; (d) add operations
that are non-generic (e.g. y-bits, field arithmetic) only if a mechanism passing supply/finder accounting exists.
